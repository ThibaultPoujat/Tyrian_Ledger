# TKT-M14-01 - Add SQLite Persistence, Migrations, and Repository Boundaries

GitHub issue: #72

## Milestone

M14 - Durable Personal Data

## Goal

Create the durable local storage foundation without mixing persistence concerns
with accounting/recommendation logic.

## Functional outcome

The local application can initialize/upgrade a SQLite database and safely store
account scope, personal completed transactions, current-order state/observations,
item metadata, settings, and schema metadata.

## Dependencies

TKT-M13-01, TKT-M13-03.

## Recommended Codex configuration

Risk class: **R3 (persistence/migration)**.

- Implementation: Sol High preferred.
- Review: fresh flagship XHigh.

## Requirements

- Versioned migrations from first schema onward.
- Repository/data-access abstractions separated from UI/financial logic.
- UTC timestamps and integer-copper prices.
- Account-scoped uniqueness for external transaction IDs.
- Safe fresh-start DB creation.
- Transaction-safe writes where partial state would be harmful.
- No API key in SQLite.

Initial entities follow `docs/architecture/data-model.md`; reserve future needs
conceptually without implementing unrelated tables prematurely.

## Acceptance criteria

- [ ] Fresh DB initializes deterministically.
- [ ] Migration tests cover fresh DB and at least one upgrade path pattern.
- [ ] Duplicate completed transaction ID/account scope is rejected/upsert-safe.
- [ ] Repository boundaries prevent UI/business code from depending on raw DB implementation.
- [ ] Schema docs match implementation.
- [ ] API key cannot be persisted by this model/path.
- [ ] No FIFO/P&L logic is implemented here.

## Validation

- Run fresh-database and migration-upgrade integration tests, including
  uniqueness/account isolation, transaction rollback, and prohibited key
  persistence checks.
- Run repository-boundary/architecture tests and the relevant solution build.
- Confirm schema documentation matches the tested migration output.

## Non-goals

Accounting, market-history schema, recommendations.

## Delivery and review

Functional summary explains what data is now durable. Fresh flagship XHigh
migration/data-loss review required. Keep the summary to the required 2-6
sentences and, before delivery, update `CURRENT.md` to TKT-M14-02 or an explicit
valid handoff.
