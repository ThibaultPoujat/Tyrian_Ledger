# TKT-M22-01 - Implement Continuous Decision Loop and Actionable Local Notifications

GitHub issue: #95

## Milestone

M22 - Convenience, Hardening, and Evaluation

## Goal

Reduce repeated manual checking by continuously reconciling fresh permitted evidence into the user's effective state and surfacing only materially new or changed actions that require attention.

## Functional outcome

While the local app is running, permitted refreshes can unlock, invalidate or change Signals without forcing the owner to repeatedly inspect scanner/dashboard pages. Notifications are a delivery surface for deterministic Signals, not a parallel recommendation system.

## Dependencies

TKT-M21-03 / #94 and TKT-M21-S05 / #133.

## Recommended Codex configuration

Risk class: **R2 (stateful cross-layer)**.

Review path: **NORMAL** unless explicitly escalated under `docs/workflow/model-effort-guide.md`.

## Decision loop

On each permitted cycle, deterministically:

1. refresh endpoint/source evidence according to existing typed gateway budgets, cache behavior and conservative rate-limit policy;
2. reconcile verified ArenaNet evidence with local unconfirmed execution state from #133;
3. update available capital, inventory, orders/exposure and plan resources;
4. invalidate or recheck stale/materially changed plans;
5. generate current opportunities/plans;
6. resolve resource conflicts and attention gates;
7. expose/notify only concrete executable Signals.

## Requirements

- Reuse existing deterministic recommendation/plan rules; no opaque alert scoring.
- Notifications are a delivery surface for Signals, not a separate recommendation engine.
- De-duplicate unchanged Signals across polling/refresh cycles.
- `WAIT`, `HOLD`, `KEEP BID`, harmless undercut/outbid, matured history, unprofitable recipes and other no-action states do not create ordinary notifications.
- A passive wait may generate a new actionable Signal when a fill/account change makes the next step executable.
- Corrective actions such as cancelling an economically invalid buy order may notify when user action is required to protect capital.
- Source freshness remains endpoint-aware and truthful; do not invent a single uniform refresh age.
- Respect VERIFY entries and conservative rate/cache behavior; do not add aggressive polling based on unverified limits.
- Support local in-app notification and OS-supported notification if practical, with enable/disable controls.
- Repeated operational failure may surface a separate compact status/health condition but must not masquerade as a profit Signal.
- Existing investment/staged-exit infrastructure may remain compatible, but investment-discovery/seasonal alert expansion is deferred from 0.1.
- All user-facing notification labels, messages, reasons, errors, settings and accessibility text introduced/touched are French.

## Acceptance criteria

- [ ] No notification executes or modifies a Trading Post/game action.
- [ ] Identical unchanged Signals are not repeatedly emitted.
- [ ] A relevant account/order/fill change can unlock and emit the next concrete step.
- [ ] No-action states stay silent.
- [ ] Materially invalidated plan produces appropriate recheck/corrective Signal rather than stale instructions.
- [ ] Trigger, no-trigger, de-duplication, recovery/reset, fill-transition, reconciliation and degraded-source tests exist.
- [ ] Notification reason and intended manual action are explainable from deterministic plan evidence.
- [ ] French notification/settings copy is covered by representative UI tests.

## Validation

- Trigger/no-trigger and threshold-boundary tests.
- Duplicate suppression/recovery/reset tests.
- Fill-transition and plan-reconciliation tests.
- Conservative source-refresh/rate-policy regression tests.
- Local notification integration plus French UI/accessibility tests.

## Non-goals

- Automated trades/gameplay.
- Remote push infrastructure.
- New investment-discovery engine.
