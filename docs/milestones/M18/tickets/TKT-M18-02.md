# TKT-M18-02 - Implement the Local Market Snapshot Collector Scheduler

GitHub issue: #83

## Milestone

M18 - Owned Historical Market Dataset

## Goal

Continuously build owned market history while the local application is running,
using the existing typed gateway/request scheduler and M18 sampling policy.

## Functional outcome

The app automatically appends valid timestamped market observations, exposes
collection health, respects request limits/backoff/shutdown, and can perform a
manual one-shot collection for verification.

## Dependencies

TKT-M18-01.

## Recommended Codex configuration

Risk class: **R2 (background stateful integration)**.

- Implementation: Terra High or Sol High.
- Review: fresh Sol High; XHigh if request/data integrity changes are complex.

## Requirements

- Configurable high-interest best-price interval (initial reference ~15 minutes).
- Lower-frequency broad-universe refresh.
- Full book only when policy requests it.
- Resolve high-interest items through registered sampling sources; current
  personal orders from TKT-M14-02 are required, while later sources become
  eligible only when their owner ticket registers them.
- Reuse request budget/batching/cancellation/429/backoff infrastructure.
- Persist only complete valid observations.
- Expose last successful capture, failures, tracked count, and next run.
- Manual one-shot capture path for tests/operations.

## Acceptance criteria

- [ ] Repeated scheduled runs append observations without duplicate sampling-key corruption.
- [ ] Shutdown cancels cleanly.
- [ ] 429/temporary failure follows bounded policy and does not fabricate data.
- [ ] Collector health is queryable by local API/UI.
- [ ] Request-budget/schedule/cancellation tests pass.
- [ ] Current personal orders are eligible for the highest-priority collection tier without inventing items when that source is empty.
- [ ] Failed/partial reads leave previous history intact.

## Validation

- Run scheduler integration tests for repeat runs, cancellation/shutdown,
  request budget, batching, 429 with/without retry metadata, bounded backoff,
  partial failure, current-personal-order source composition including an empty
  source, manual one-shot capture, and health reporting.
- Run persistence integrity tests proving only complete observations append and
  prior history survives failure.
- Review/update VERIFY-004, VERIFY-005, VERIFY-006, VERIFY-010, and VERIFY-011;
  use safe provisional limits when authoritative evidence remains unavailable.

## Operational handoff

After merge, keep the collector running during later development whenever
practical so useful history accumulates.

## Non-goals

Retention/downsampling, historical analytics, or claiming unverified ArenaNet
quota/retry behavior as fact.
