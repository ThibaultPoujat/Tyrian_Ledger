# TKT-M18-01 - Add Durable Market-History Schema and Adaptive Sampling Policy

GitHub issue: #82

## Milestone

M18 - Owned Historical Market Dataset

## Goal

Create the durable historical-market foundation without over-collecting every
order book at full frequency.

## Functional outcome

Tyrian Ledger has a versioned schema and explicit policy for which markets to
observe, how often, what cheap best-price data to retain, and when detailed
books justify their storage/request cost.

## Dependencies

TKT-M14-02, TKT-M17-03.

## Recommended Codex configuration

Risk class: **R3 (persistence/data policy)**.

- Implementation: Sol High preferred.
- Review: fresh flagship XHigh.

## Persist at minimum

Best-price observations:

- UTC timestamp;
- item ID;
- highest buy/lowest sell copper;
- aggregate buy/sell quantity;
- source freshness/status;
- sampling tier/policy version.

Design detailed order-book storage separately because it is materially larger.

## Sampling policy

Support tiers such as:

1. current personal orders, plus held positions once TKT-M20-03 registers that
   source;
2. watchlist/approved markets;
3. broad tradable universe at lower frequency;
4. full order books for shortlisted/high-interest markets only.

Sampling inputs are capability-driven. M18 consumes current personal-order IDs
from TKT-M14-02 and exposes a typed/extensible source contract so later features
can add priority items without rewriting the scheduler. Held positions do not
exist during M18; TKT-M20-03 owns registering open positions and removing their
position-derived eligibility when they close.

## Acceptance criteria

- [ ] Versioned migration adds efficient item/time-window history indexes.
- [ ] Sampling policy is configurable/testable and does not assume one fixed rate for all items.
- [ ] Current personal orders from TKT-M14-02 enter the highest-priority tier; an empty source remains explicit and valid.
- [ ] Priority-source composition is extensible without coupling M18 to future position persistence.
- [ ] Full-book storage is explicit rather than accidentally captured everywhere.
- [ ] Storage-growth estimate for representative policies is documented.
- [ ] UTC/integer-copper invariants hold.
- [ ] Future retention/downsampling can evolve without corrupting existing history.
- [ ] Scheduler loop is not implemented in this ticket.

## Validation

- Run fresh/upgrade migration, index/query, uniqueness, timestamp, integer-
  copper, and representative retention-evolution tests.
- Test sampling-tier selection/configuration, current-personal-order source
  composition including an empty source, extensible source registration, and
  detailed-book opt-in behavior.
- Reproduce and review the documented representative storage-growth estimate.

## Non-goals

Running the collector loop, destructive retention, historical analytics, or
collecting every full order book.
